| 环节 | 当前事实 | 对新需求的影响 |

| BE 行清理 | 使用 `tenant_column_unique_id` 定位列，检查 `VARCHAR`，构造 IN 谓词 | 不依赖列名叫 `tenant`；整数需要扩展准入及类型处理 |

其他边界仍需作为本次调研的基线：业务表为本地 shared-nothing `DUP_KEYS` 基础表，无 Rollup/同步物化索引；时间列固定 `recordTimestamp BIGINT` Unix 秒，采用受支持的 Range/List 分区。FE 以分区时间上界证明某个绑定值在整个分区过期，BE 不做逐行时间判断。字符串保持精确字节匹配，不做大小写、空格、Unicode、IPv6 文本归一化或 CIDR 匹配。

默认过滤名单上限为 100000 个值、序列化 8 MiB；策略导出默认最多 1000000 行，仍受字节及内存上限约束。本次保留这些上限，容量边界的实际测试见第 050 轮验收记录；不把 IP/设备扩展视为容量扩容。

## 3. “同步调整 FE 校验和 BE 导出”的含义

这里的“同步”指两处实现一并适配，不是新增实时同步服务。

现有策略链路为：

```text
策略源表
  → Dictionary 刷新成功，策略保存在 BE Dictionary Cache
  → BE 导出指定成功版本的策略内容给 FE
  → FE 构建完整策略快照，计算过期值/保留值名单
  → BE 按名单清理业务表
```

例如把策略第一键列从 `tenant` 改成 `device_name`：

1. FE 当前会在绑定时因名称不符合契约而拒绝，需要让它认可新的第一键列定义。
2. 即使 FE 已放开，BE 导出端仍检查第一列必须叫 `tenant`，会返回 `SCHEMA_MISMATCH`，FE 仍得不到可用快照。
3. 因而两端必须使用同一套键角色、名称和类型契约。不能简单删光校验，仍需验证键数量、顺序、类型以及值列含义。

这里导出的是 TTL 策略条目，不是把业务表行或 IP 日志导出给 FE。上述导出路径本来就存在。仅放开 VARCHAR 列名，通常不需要改变名单的数据表示或 Rowset 清理算法。

## 4. 后续阶段保留：整数支持调研（不纳入第一阶段）

本节保留此前讨论，不要求第一阶段完成或继续细化。已确认的后续方向是：整数与字符串分别组织策略表/Dictionary，同类型可共用；整数默认 TTL 不放在策略表，由业务表属性提供。整数类型清单、宽度兼容、编码与数值 IP/IPv6 范围，以及 `compaction_ttl` 是否指现有 `default_days` 均尚未最终确定。

### 4.1 类型表示的方案比较与当前对齐方向

以下保留两条路径的历史比较。用户已认可整数和字符串分别组织策略表/Dictionary，并明确整数默认 TTL 由表属性提供；后续若重启整数支持调研，再对齐具体类型清单和实现契约。

| 路径 | 示例 | 相对工作量与取舍 |
| --- | --- | --- |
| A：业务列支持整数，策略键继续 VARCHAR | 业务 `device_id BIGINT = 123`；策略第一键保存规范十进制字符串 `'123'` | 已不再优先推荐；增加文本转换、冲突检测和配置生效状态的负担 |
| B：业务列和策略键都支持原生整数 | 业务 `device_id BIGINT`；策略第一键 `BIGINT` | 后续候选方向；需扩展导出类型/编码契约，默认 TTL 已明确由表属性提供，无需设计整数默认策略行 |

路径 A 曾作为减少结构改动的候选。用户随后指出跨类型配置不自然，且不能依赖用户不写入 `'001'`、`'1'` 等不同文本，因此不再优先推荐。若后续恢复整数支持，优先按路径 B 讨论。业务列与策略键是否严格要求相同整数宽度等细则，仍待类型清单与绑定规则对齐。路径 B 不意味着重写普通 Dictionary 的全部缓存机制；现有通用键编码能力可复用，专用 Tenant-TTL 导出契约仍需扩展。

### 4.2 整数支持需要处理的工作

1. **确定支持类型及范围。** 明确是否只做 `INT/BIGINT`，还是包括 `TINYINT/SMALLINT/LARGEINT`，校验策略值是否落在目标列的有效范围内，拒绝溢出和截断。业务设备 ID 的负数含义由业务定义，不能擅自只支持正整数。
2. **确定相等关系及编码。** 路径 A 中，`'001'` 和 `'1'` 是两个不同的字符串主键，转成整数后却都指向 1，必须处理冲突。路径 B 中，策略键本身就是整数 1；若输入文本经正常整数转换成功存入该列，文本写法不再成为身份的一部分。相同整数键和逻辑表键是同一主键，重复写入按既有 PRIMARY KEY 表更新规则处理，TTL 无需再仲裁两个文本键。VARCHAR 绑定继续保持精确字节语义，`'001'` 和 `'1'` 仍是不同业务值。
3. **保持有类型的绑定和任务契约。** 持久化/指纹/任务验证需要能区分绑定类型，发现类型漂移必须拒绝旧计划。现有 RPC 字节字段可以保留或扩展，但整数表示必须有明确约定，不能让接收端猜测字节含义；是否新增字段及版本由设计阶段决定。
4. **扩展 BE 准入和谓词。** 当前专用过滤器拒绝非 VARCHAR；通用 `new_column_in_predicate` 已支持整数类型，可复用。建议把名单常量校验/转换为目标类型，再构造数值谓词，不对每一行业务值做字符串 CAST。ZoneMap、NULL 处理和精确匹配需用新增回归验证。
5. **调整状态查询和错误信息。** 查询某个 ID 的策略时，应能按目标类型解析，并报告非法值、越界、策略不兼容等原因；兼容原字符串查询。
6. **扩展测试。** 包括最小/最大值、0、负数、溢出、NULL、策略更新、列类型变化及实际删除结果。原生整数方案还需覆盖相同数值更新同一策略主键，以及字符串绑定仍区分 `'001'` 和 `'1'`；若保留跨类型方案，再增加文本转换和转换后冲突测试。业务写入端的具体文本转换规则沿用正常类型写入语义，不由 TTL 推导新的隐式转换能力。

沿路径 B 还需要：BE 根据实际键类型读取值，替代第一键固定 `get_slice()`；FE 快照接收并区分类型。整数表级默认 TTL 已明确由业务表属性提供，不新增整数默认策略行、默认标记列或默认策略 Dictionary，也不占用 0、-1 等合法整数作为哨兵。这使整数类型扩展可以继续围绕“绑定值 + 逻辑表键 → 保留天数”的三列策略结构设计。

### 4.3 数值 IP 的额外边界

- 如果业务已经用 BIGINT 保存 IPv4 数值，TTL 可以把它当普通整数精确匹配，不必增加网络地址解析。
- IPv4 全值域为 0～4294967295，不能全部装入有符号 32 位 INT；BIGINT 可以容纳。既有数据若使用有符号 INT 的位模式表示，需按实际存储约定讨论，不能默认重解释。
- IPv6 涉及 128 位地址，不能笼统当作 BIGINT 支持。需先明确字符串、二进制或其他既有表示，另定类型和转换范围。
- 允许输入点分 IP 文本去匹配整数列、支持 CIDR 或地址范围，都是额外需求，不因支持整数列而自动提供。

### 4.4 当前判断

单列整数支持的工作量明显高于只放开 VARCHAR 列名，但主要增加在类型校验、策略表示、传输契约和回归验证。现有分区 TTL 判断、调度框架、保留行范围和 Rowset 原子替换可以作为复用基础。此判断来自静态阅读，不是完成适配或性能验证的结论。

### 4.5 关于“能否禁止用户配置”的进一步澄清

当前 TTL 绑定和快照处理不是策略源表的通用写入约束。若第一键定义为 VARCHAR，普通写入可以保存 `'001'` 和 `'1'`，不能仅凭 TTL 绑定承诺在源头禁止这些记录。

技术上可以在 TTL 采用策略之前做校验，但这是拒绝候选策略生效，不是阻止用户写入源表。若采用路径 A 且将转成同一整数但 TTL 不同的记录视为冲突，就必须明确定义错误提示、失败范围和继续使用上一成功策略等行为，不能静默选取其中一条，也不能把转换失败当作未配置而直接走默认 TTL。这会增加使用和运行状态的复杂度，不能仅用文档要求用户填规范数字来解决。

当前建议是把类型一致作为候选绑定规则，例如 `INT ↔ INT`、`BIGINT ↔ BIGINT`、`VARCHAR ↔ VARCHAR`；整数宽度及 VARCHAR 长度兼容规则另议，不将名称可不同推导为值类型可任意转换。用户已确认：一个策略键列只有一种类型，整数和字符串使用相应类型的策略表/Dictionary；同类型业务表仍可通过逻辑表键共用策略。不要求一个 Dictionary 混合承载字符串和整数策略。

用户已进一步明确整数表级默认 TTL 不在策略表配置，而由表属性提供。这一最新决定替代此前“为整数另行设计 Dictionary 表级默认记录”的待讨论方向，具体规则见下一节。

### 4.6 整数表级默认 TTL：已确认语义与待核对语法

已确认的产品语义：

1. 整数策略表只保存具体整数值在指定逻辑表键下的专属保留天数。
2. 在成功且有效的策略快照中，命中整数值专属策略则使用该策略；没有命中时，使用业务表属性配置的默认 TTL。
3. 整数键不提供 Dictionary 表级 `default` 记录，也不使用 0、-1、NULL 或其他合法/特殊整数值代替默认记录。
4. 整数和字符串策略分别组织；本次关于整数默认值的决定不取消字符串策略现有的 `('default', table_key)` 回退。

两类策略的解析顺序为：

```text
整数：具体整数值专属策略 → 业务表属性默认 TTL
字符串：具体字符串值专属策略 → Dictionary 表级 default → 业务表属性默认 TTL
```

继续沿用当前故障边界：没有可用成功快照、绑定失效或策略内容不能验证，不等同于“没有专属记录”，不得因此绕过校验使用默认 TTL 清理。NULL 也不是普通未命中的整数值，仍以现有保守清理语义为基线；本轮没有确认将 NULL 直接按表属性默认 TTL 删除。现有 `retention_days = 0` 的忽略规则作为基线，整数对应条目被忽略后视为无有效专属策略。

属性语法待核对：用户将该表属性称为 `compaction_ttl`。当前 FE 代码未定义同名独立属性，默认天数实际来自：

```sql
"compaction_retention_condition" =
    "dictionary_ttl('policy_dict', 'business.table_key', 180)"
```

其中第三个参数 `180` 是现有 `default_days`，单位为天。需要确认用户意图是复用这个参数，还是新增独立的 `compaction_ttl` 属性。语法确认前，不将新属性当成已支持能力，也不同时设计两套默认值优先级。由属性提供默认值的语义已确认，不因属性命名待核对而重新作为未决需求。

对实现适配的影响：整数 `TablePolicy` 无 Dictionary 表级默认项；有效默认值取业务表配置。FE 的默认策略来源展示、保留/删除名单选择、到期事件、策略指纹、修改属性后的重新评估及相关验收均需与该规则一致。整数默认策略无需新增源表列或单独默认策略导出结构；类型识别和整数值传输仍需实现。

## 5. 空字符串的影响

本轮确认的空字符串指长度为零的字符串 `''`；它与 NULL、一个空格 `' '`、字符串内的 NUL 字节不同。

### 5.1 现状区分

- **业务数据出现 `''`：** 当前没有要求业务列内容非空的准入校验；有效策略中没有该值的专属条目时，它作为未命中值走默认 TTL，不等同于 NULL。已有 BE 行过滤测试数据包含 `''`，但该用例只证明其他值被过滤时它被保留，并未覆盖空字符串专属策略的完整链路。
- **策略表为 `''` 配置专属 TTL：** 当前 FE 快照 Builder 拒绝空键；Planner 和 Agent 任务构造也有对应拒绝，需要一并适配。

### 5.2 用户已确认的空字符串语义

把 `''` 当普通字符串绑定值：可以配置专属 TTL；未配置时继续默认回退；不占用 `default` 的含义，与 NULL 区分。本次确认不将空字符串映射为整数 0，也不改变整数列的写入规则。NULL 具体清理行为继续以现有实现为基线，未提出扩展。

支持空字符串专属策略需要的主要改动为：

1. 移除 SnapshotBuilder、Planner、CompactionTask 对绑定值长度为零的禁止，保留字段缺失、NULL 以及逻辑表键非空等检查。
2. 验证 Dictionary 导出、Protobuf/Thrift、FE Map 和指纹的完整往返能保留零长度值，不将其误当作缺失字段。
3. 区分 `[]`（空名单）与 `[""]`（含一个空字符串值的名单）。现有 BE 对空名单的限制继续有效，不能为了支持空字符串而放开空 KEEP_LIST。
4. 验证 DELETE_LIST、KEEP_LIST、NULL、空格、默认回退、零天数策略忽略、状态查询和 ZoneMap 裁剪。

相对判断：属于较小且局部的适配，无需增加新值类型或修改分区 TTL 算法；仍需补全专项测试，不能只删除一处校验后宣称支持。

### 6.3 已确认：旧 SHOW 兼容与通用入口

用户已确认保留旧入口，同时增加面向通用绑定列的入口。以下是需求契约，第 048 轮已实现新增入口。

当前已有语法：

```sql
SHOW TENANT TTL STATUS FROM business.http_log;
SHOW TENANT TTL STATUS FROM business.http_log FOR TENANT '10.0.0.1';
```

扩展后的兼容解释：

1. 旧入口在绑定 `tenant`、`dst_ip` 或 `device_name` 的表上都可用，不只为旧 tenant 表保留。
2. `FOR TENANT 'x'` 中的 `'x'` 表示该表实际绑定列的一个值，不因此重新选择物理列 `tenant`。例如表绑定 `dst_ip` 时，上例查询 IP `10.0.0.1` 的有效 TTL。
3. 保留旧入口的结果列名称、顺序、类型和已有 `ResolutionType` 值，避免破坏按列名、位置或状态值解析的脚本。旧 `TenantColumnId`/`TenantColumnUniqueId` 对应实际绑定列身份，`Tenant` 对应该次查询值。
4. 没有 `FOR` 子句为表级查询，`FOR TENANT ''` 为显式查询空字符串值；两者必须区分。查询空字符串仍需完成本次空键适配，不能凭解析器可接受就宣称完整链路已支持。

第 048 轮新增通用入口：

```sql
SHOW COMPACTION TTL STATUS FROM business.http_log;
SHOW COMPACTION TTL STATUS FROM business.http_log FOR VALUE '10.0.0.1';
SHOW COMPACTION TTL STATUS FROM business.http_log FOR VALUE '';
```

通用入口复用同一状态服务、策略快照、匹配规则和表 SELECT 权限，不增加业务数据扫描。通用结果使用 `KeyColumn`、`DictionaryKeyColumn`、`Value` 等名称展示实际绑定，继续提供 `EffectiveRetentionDays`、策略来源和现有调度/快照诊断。完整字段映射在编码计划中明确；这是同一服务的两种展示格式，不宣称两者结果元数据完全相同。

新文档和新脚本使用通用入口，已有脚本继续使用旧入口；第一阶段不删除旧语法。

### 6.4 D01 最终确认：先解除、再重新启用

用户已确认采用两步变更，禁止直接将业务绑定列改为另一列。删除的是业务表的 TTL 配置与绑定，不删除业务表、策略表或 Dictionary。重新启用复用已有准入流程，两步之间该表不生成新的 TTL 清理计划；重新启用失败时保持未绑定状态。

该决定替代此前“待生效配置、等旧计划结束后在调度入口换列”的方案；不再增加 PENDING 绑定、延迟生效状态机或全副本收敛屏障。新开放解除绑定 DDL，取代历史文档中“首期不提供禁用 DDL”的限制；解除入口已按第 6.6 节 E01 确认，第 049 轮已实现。

1. 解除 DDL 成功表示配置、绑定和相关引用已解除，FE 旧上下文及完成进度失效；不表示 BE 已下发任务结束、撤销或回滚。
2. 新绑定可以立即登记，实际清理由后续现有 TTL 调度触发，不因新建绑定额外启动并行调度器。
3. 同一 BE、同一 Tablet 上旧任务正在执行时，新任务返回 TABLET_BUSY，FE 按现有有界预算重试；预算耗尽则本轮失败，后续重新评估，不恢复旧绑定。
4. 不同 Tablet 或不同副本可以执行新旧任务，没有全表顺序保证；同一 Tablet 只有执行互斥，没有按绑定新旧排序的保证。
5. 旧请求在网络中延迟、或已有补发晚到时，即使新任务已经完成，旧请求仍可能被接受并按原绑定列删除。允许这种行为，不增加持久化代际、发送撤回或旧请求屏障。
6. 旧规则已删除的行不恢复；新规则认为应保留的行仍可能被迟到旧请求删除。副本差异可能长期存在，后续新策略调度不保证修复。
7. 旧回报不能推进新绑定进度；需明确作废 FE 旧执行上下文，不能仅依赖列名或属性值不同，覆盖解除后又绑定到完全相同配置的情况。
8. FE 重启按日志恢复已解除或已重新启用的真实配置，不恢复逐副本旧任务账本；BE 旧任务按现有执行边界自然结束。
9. 验收按每个副本实际执行的请求和数据历史验证精确删除，不以最终各副本相同为两步变更的通过条件。列身份、Schema、分区证明和单次提交原子性要求不放宽。

### 6.5 D02 最终确认：绑定期间禁止重命名该列

用户已确认：TTL 绑定期间禁止重命名该绑定列；需要改名时，先解除 TTL，执行普通列重命名，再重新绑定。此决定替代之前“同一列改名后自动延续 TTL 绑定”的设计。

限制针对实际业务绑定列的身份，无论当前是否已有快照、调度是否开启，只要尚未解除绑定就拒绝其改名。其他未绑定列仍按 StarRocks 既有规则处理。解除后普通重命名是否允许，也由原有 Schema/分区等规则决定；本需求不放宽普通 DDL 准入。

不新增 TTL 随改名同步更新属性、扩展 ColumnRenameInfo 或迁移分区表达式指纹的机制。解除后重新启用按新列名重新做完整准入并保存身份。BE 已下发任务仍受第 6.4 节的晚到请求与原有 Schema 检查约束。

本项不扩展业务表名、Dictionary 名称或策略源表键列的重命名语义。业务表改名和逻辑表键关系继续沿用已有契约，不自动修改 table_key。
