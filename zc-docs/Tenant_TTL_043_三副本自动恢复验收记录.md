## 环境与复用产物

- 隔离 Docker 网络 `sr-ttl-r043`：3 个投票 FE、3 个 BE，业务表及策略表均为三副本；每个节点保留独立持久数据卷。
- FE 使用 042 完成后的增量 package。BE 复用现有 Debug、MAKE_TEST=OFF 二进制，本轮无 BE 产品修改；显式配置 `tenant_ttl_policy_export_max_rows=1000000` 补齐历史二进制与后续配置默认值的差异。SHA-256 与来源保存在 `multireplica/artifacts/binaries.json`。
- 运行节点只读挂载编译缓存卷，编译写入者仍只有 `starrocks-tenant-ttl-e2e`。未执行 clean、删除编译目录或构建卷。
- 基本测试调度间隔 10 秒；故障准备阶段仅当前 Leader 暂设 180/600 秒，避免基线装载期间提前清理，随后恢复。自动恢复开关及 300 秒冷却遵循产品默认，E08 单独验证动态关闭和重新开启。
- 自动 List 表存在一个没有显式值的内部空占位分区，安全地保持不可证明；不将它计入 12 个业务时间分区。SHOW 可能显示 `FAIL_CLOSED`，验收单独核对全部业务分区、副本及完整成功进度。

## 验收口径

每个标准场景两张表各 120,000 行；E01/E03/E06 追加每表 1,200,000 行。故障前完整读取每张表 48 个 Tablet、144 个 Replica；普通策略处理后逐个读取每张表 36 个 Tablet 的 108 个 Replica；策略收紧后为 24 个 Tablet、72 个 Replica。

每次定向读取保存 SQL、EXPLAIN 和实际执行 Profile，确认扫描到预期 BE、Tablet、Replica。以故障前全部业务列独立生成保留与删除的多重集合，执行完整双向差集；同时核验无 hint 的全表明细、聚合和对照表。整分区 DROP 检查 Catalog 缺失及全表无残留。不以 API 成功、ACTIVE、总行数或单个副本代替数据通过。

## 本轮边界

- 真实集群为 shared-nothing 的 3 FE / 3 BE，没有运行 CN 实机容灾；BE/CN 公共候选遍历的代码分支由 FE 定向单测覆盖。
- 没有全 FE / 全 BE 测试、重新运行所有 Sanitizer、长时间稳定性或吞吐基准。本轮扩大数据量用于验证删除正确性，不作为性能承诺。
- 没有新增节点级缓存主动补齐。可用的旧 FE 快照继续驱动 TTL；旧快照长期追不上更新策略时的恢复刷新，按已确认范围留到下一轮。
- 本轮无产品代码修改；相关实现仅在 041、042 两个独立提交。043 的客户端错误修正不回改已通过的产品二进制，失败日志保留，不将只完成恢复或计数匹配的中间态记为验收通过。
