# StarRocks Tenant-TTL 编译、启动与跑测

## 1. 文档范围

本文记录当前开发机上 StarRocks BE 的实际编译和测试方式，供 Tenant-TTL Compaction 首轮开发使用，覆盖：

- macOS 宿主机与 Colima/Linux 编译环境的边界。
- Linux dev-env 编译容器的创建、启动和停止。
- BE Debug/Release 编译与特殊 HTTP 测试入口构建。
- BE 单元测试的定向运行方式。
- 使用本地构建产物打包并启动独立 shared-nothing all-in-one 集群。
- SQL、HTTP 和 SQL Tester 的基本验证入口。

本文不描述 FE 正式下发 Tenant-TTL Agent Task，也不替代 Tenant-TTL 的详细编码计划和测试用例设计。

## 2. 当前环境与边界

当前环境已经核实如下：

- 宿主机为 macOS ARM64，不能直接运行 Linux BE。
- `output/be/lib/starrocks_be` 是 Linux ARM64 ELF 文件。
- macOS 当前没有可直接使用的 CMake、Protobuf/Thrift 和 StarRocks thirdparty 工具链。
- Colima Linux VM 为 ARM64，VM 内安装了 Docker。
- Tenant-TTL 4.0 分支使用 `starrocks/dev-env-ubuntu:4.0-latest` ARM64 编译镜像；该镜像提供 GCC 12.3、Protobuf 3.14，并设置 `STARROCKS_THIRDPARTY=/var/local/thirdparty`。不得改用不带 4.0 标签的 `latest`，否则生成代码和 thirdparty ABI 可能不匹配。
- 源码目录 `/Users/zhuchong/Documents/code/starrocks-main` 在 Colima VM 内可见，可以 bind mount 到编译容器。
- C++ 编译、BE 单测和 BE 进程运行必须在 Linux 容器中完成；macOS 只负责编辑源码、发起 SSH/Docker 命令以及运行 MySQL/curl 客户端。

2026-09-04 已停止以下旧测试容器：

- `sr413-dictionary-ttl-20260831`
- `starrocks-quickstart`
- `starrocks-partition-memory-20260820`

停止后 `docker ps` 为空。只停止了容器，没有停止 Colima VM 或 Docker 引擎，也没有删除容器、镜像或数据卷。

Tenant-TTL 测试必须使用新建的专用容器、端口和测试表，不复用以上旧集群。

## 3. 宿主机变量与 Colima 检查

在 macOS 终端中设置本次使用的路径和名称：

```bash
SR_ROOT=/Users/zhuchong/Documents/code/starrocks-main
COLIMA_SSH_CONFIG=/Users/zhuchong/.colima/_lima/colima/ssh.config
BUILD_CONTAINER=starrocks-tenant-ttl-4.0-build

RUNTIME_IMAGE=starrocks/allin1-ubuntu:tenant-ttl-local
```

确认 Colima VM、CPU 架构和 Docker 服务正常：

```bash
ssh -F "$COLIMA_SSH_CONFIG" lima-colima \
  'uname -m && docker version --format "{{.Server.Arch}} {{.Server.Version}}"'
```

预期架构为 `aarch64`/`arm64`。如果 SSH 失败，应先从本机 Colima 应用启动 Colima；当前 shell 没有独立的 `colima` CLI，不应假设 `colima start` 可用。

确认编译镜像存在：

```bash
ssh -F "$COLIMA_SSH_CONFIG" lima-colima \
  'docker image inspect starrocks/dev-env-ubuntu:4.0-latest \
   --format "{{.Os}}/{{.Architecture}} {{json .Config.Env}}"'
```

## 4. 创建和管理编译容器

### 4.1 首次创建

编译容器只承载工具链。当前验证环境将宿主源码只作为同步源挂载到 `/host-workspace`，实际编译使用容器内隔离副本 `/tenant-ttl-workspace`，避免宿主机遗留的 `gensrc/build` 被另一版 Protobuf 生成后污染 4.0 构建：

```bash
ssh -F "$COLIMA_SSH_CONFIG" lima-colima \
  "docker run -d \
    --name '$BUILD_CONTAINER' \
    --mount type=bind,src='$SR_ROOT',dst=/host-workspace \
    --workdir /tenant-ttl-workspace \
    starrocks/dev-env-ubuntu:4.0-latest \
    bash -lc 'trap : TERM INT; sleep infinity & wait'"
```

确认源码挂载和工具链：

```bash
ssh -F "$COLIMA_SSH_CONFIG" lima-colima \
  "docker exec '$BUILD_CONTAINER' bash -lc '
    uname -m
    gcc --version | head -n 1
    cmake --version | head -n 1
    test -f /tenant-ttl-workspace/build.sh
    test -d \"\$STARROCKS_THIRDPARTY\"
  '"
```

### 4.2 已存在时重新启动

先检查状态：

```bash
ssh -F "$COLIMA_SSH_CONFIG" lima-colima \
  "docker ps -a --filter name='^/$BUILD_CONTAINER$' \
   --format '{{.Names}} {{.Status}}'"
```

如果容器存在但已停止：

```bash
ssh -F "$COLIMA_SSH_CONFIG" lima-colima \
  "docker start '$BUILD_CONTAINER'"
```

### 4.3 停止编译容器

```bash
ssh -F "$COLIMA_SSH_CONFIG" lima-colima \
  "docker stop '$BUILD_CONTAINER'"
```

停止不会删除 `be/build_*`、`be/ut_build_*` 或 `output/`，后续启动后仍可增量编译。不要为了普通编译失败直接删除整个 workspace 或运行宽范围清理命令。

首次创建隔离副本时应排除宿主机的 `.git`、`output` 和 `gensrc/build`，再在隔离副本中指向宿主 `.git`。生成代码必须由 4.0 镜像重新生成。日常修改先落到宿主源码，再同步本轮涉及的文件到隔离副本；不得反向覆盖用户工作区中的其他改动。

## 5. 编译 StarRocks

以下命令均从 macOS 发起，但实际在 Linux 编译容器中执行。

### 5.1 编译前检查

```bash
cd "$SR_ROOT"
git status --short
git rev-parse HEAD
```

必须保留并避开用户已有修改。开始一次较长编译前记录 HEAD，便于确认二进制对应的源码版本。

### 5.2 首次准备匹配的 FE 和 BE 产物

all-in-one 镜像会同时复制 `output/fe` 和 `output/be`。首次准备运行环境时，应在同一个源码版本上至少完整构建一次 FE 和 BE：

```bash
ssh -F "$COLIMA_SSH_CONFIG" lima-colima \
  "docker exec '$BUILD_CONTAINER' bash -lc '
    cd /workspace
    BUILD_TYPE=Debug ./build.sh --fe --be -j8
  '"
```

这一步较慢，但可以避免把新 BE 与历史遗留的 FE 产物打包到同一镜像。

### 5.3 日常 BE Debug 增量编译

```bash
ssh -F "$COLIMA_SSH_CONFIG" lima-colima \
  "docker exec '$BUILD_CONTAINER' bash -lc '
    cd /workspace
    BUILD_TYPE=Debug ./build.sh --be -j8
  '"
```

`build.sh` 不带 `--clean` 时会复用 `be/build_Debug`。普通开发循环不要使用 `--clean`；只有确认 CMake 缓存或生成代码已经无法增量恢复时才做针对性清理。

如果只做快速 C++ 编译检查，可以临时增加 `--without-java-ext`：

```bash
BUILD_TYPE=Debug ./build.sh --be --without-java-ext -j8
```

但在打包可运行 all-in-one 镜像前，应再执行一次不带 `--without-java-ext` 的完整 BE 构建，保证运行包完整。

### 5.4 默认 Release 构建

用于验证发布构建和 HTTP 手工入口隔离：

```bash
ssh -F "$COLIMA_SSH_CONFIG" lima-colima \
  "docker exec '$BUILD_CONTAINER' bash -lc '
    cd /workspace
    BUILD_TYPE=Release ./build.sh --be -j2
  '"
```

默认构建不得包含 Tenant-TTL 手工 HTTP Handler 的符号和路由字符串。

### 5.5 Tenant-TTL 手工 HTTP 入口构建

第 5 轮已实现该构建开关：

- CMake option：`ENABLE_TENANT_TTL_MANUAL_TEST_ENDPOINT`，默认 `OFF`。
- C++ 编译宏：`STARROCKS_TENANT_TTL_MANUAL_TEST_ENDPOINT`。
- `build.sh` 参数：`--enable-tenant-ttl-manual-test-endpoint`。
- `build.sh` 每次配置 CMake 时显式传递 `ON` 或 `OFF`，不能依赖上一次 CMake cache。

当前 8 CPU/24 GiB Colima 环境的专项 Release 构建命令为：

```bash
ssh -F "$COLIMA_SSH_CONFIG" lima-colima \
  "docker exec '$BUILD_CONTAINER' bash -lc '
    cd /tenant-ttl-workspace
    BUILD_TYPE=Release ./build.sh \
      --be \
      --without-java-ext \
      --enable-tenant-ttl-manual-test-endpoint \
      -j2
  '"
```

上述 `--without-java-ext` 只适用于把新 native BE 二进制替换到已经含有匹配 Java extension 的 4.0.11 测试镜像。如果要从 `output/` 独立打包完整运行镜像，必须去掉该参数后重新构建。

该开关只让 `be/src/http/CMakeLists.txt` 编译特殊 Action，并只为 `Webserver`、`ServiceBE` 定义路由所需宏；正常存储执行链不受宏保护。默认 OFF 构建不会编译 Action，也不会注册 `/api/tenant_ttl_compaction/run`。

### 5.6 构建结果检查

```bash
file "$SR_ROOT/output/be/lib/starrocks_be"
stat -f '%Sm %N' -t '%Y-%m-%d %H:%M:%S' \
  "$SR_ROOT/output/be/lib/starrocks_be"
```

预期为 Linux ARM64/aarch64 ELF。该文件不能在 macOS 直接执行。

## 7. BE 单元测试

### 7.1 标准入口

BE 单元测试统一通过仓库根目录的 `run-be-ut.sh` 运行。该脚本负责：

- 配置 `be/ut_build_<BUILD_TYPE>`。
- 增量编译测试程序。
- 准备 `LD_LIBRARY_PATH`、JVM、Hadoop classpath、test data 和 ASAN 环境。
- 对 `starrocks_test` 或独立测试二进制应用 GTest filter。

除专门调试外，不建议绕过脚本直接执行 `starrocks_test`，否则容易遗漏运行时环境。

### 7.2 Tenant-TTL 定向 ASAN 测试

首选命令：

```bash
ssh -F "$COLIMA_SSH_CONFIG" lima-colima \
  "docker exec '$BUILD_CONTAINER' bash -lc '
    cd /workspace
    BUILD_TYPE=ASAN ./run-be-ut.sh \
      --module starrocks_test \
      --gtest_filter=\"TenantTtl*\" \
      --without-java-ext \
      -j8
  '"
```

`run-be-ut.sh` 在没有显式 `BUILD_TYPE` 时也默认使用 ASAN；文档中显式写出，避免误判实际构建类型。

如果按单个测试 suite 运行：

```bash
BUILD_TYPE=ASAN ./run-be-ut.sh \
  --module starrocks_test \
  --test TenantTtlCompactionTest \
  --without-java-ext \
  -j8
```

`--test NAME` 会转换成 `NAME*`。需要精确选择多个 suite/case 时使用 `--gtest_filter`：

```bash
BUILD_TYPE=ASAN ./run-be-ut.sh \
  --module starrocks_test \
  --gtest_filter='TenantTtl*:*FilteredRowsetWriter*:*VerticalSegmentRewriter*' \
  --without-java-ext \
  -j8
```

测试 suite 的最终名称以实际新增代码为准；以上名称是本项目约定的命名前缀。

### 7.2.1 Tenant-TTL 独立测试目标的快速循环

Tenant-TTL 专项用例登记为 `ADD_BE_TEST` 独立目标，以避免每一轮都重新编译统一 `starrocks_test` 中数百个无关测试源。已完成一次 CMake 配置和依赖库构建后，可在隔离工作区中只增量构建指定目标：

```bash
cd /tenant-ttl-workspace
export STARROCKS_HOME=/tenant-ttl-workspace
source env.sh
cmake --build be/ut_build_Release \
  --target tenant_ttl_compaction_types_test \
           tenant_ttl_compaction_fixture_test \
  -j2
```

本机 Colima 当前给编译容器分配 8 CPU、24 GiB 内存；Release 首次构建使用 `-j2`，避免大型 C++ 翻译单元并发导致 OOM。直接执行独立测试二进制时必须复用 `run-be-ut.sh` 的运行环境，并先执行 `ulimit -n 65535`；需要 StorageEngine 的测试应使用 `testutil/init_test_env.h` 初始化标准测试环境。快速独立目标用于每轮开发反馈，首批实现收口仍需运行统一 `starrocks_test` 回归。

### 7.3 Debug 单测

需要调试而不希望使用 ASAN 时：

```bash
BUILD_TYPE=Debug ./run-be-ut.sh \
  --module starrocks_test \
  --gtest_filter='TenantTtl*' \
  --without-java-ext \
  -j8
```

Debug 和 ASAN 使用不同构建目录，可以并存：

```text
be/ut_build_Debug
be/ut_build_ASAN
```

### 7.4 扩大回归范围

完成一轮功能后，先跑 Tenant-TTL 及直接依赖组件，再执行整个 `starrocks_test`：

```bash
BUILD_TYPE=ASAN ./run-be-ut.sh \
  --module starrocks_test \
  --without-java-ext \
  -j8
```

完整 BE UT 成本高，不作为每次小修改的必跑项，但必须在首批实现收口时执行。若只想确认会选择哪些测试，可以使用 `--dry-run`；该参数跳过执行，但仍会完成测试程序构建。

### 7.5 单测产物和日志

主要位置：

```text
be/ut_build_ASAN/test/starrocks_test
be/ut_build_Debug/test/starrocks_test
log/
```

普通失败优先保留完整命令输出和 `log/`；ASAN、LSAN 或 core 问题还要记录构建类型、GTest filter、HEAD 和失败 case。

## 8. 使用本地产物启动独立 all-in-one 集群

### 8.1 打包运行镜像

确认 `output/fe` 和 `output/be` 都来自需要测试的源码版本后，在 Colima VM 中从仓库根目录构建：

```bash
ssh -F "$COLIMA_SSH_CONFIG" lima-colima \
  "cd '$SR_ROOT' && \
   DOCKER_BUILDKIT=1 docker build \
     --build-arg ARTIFACT_SOURCE=local \
     --build-arg LOCAL_REPO_PATH=. \
     -f docker/dockerfiles/allin1/allin1-ubuntu.Dockerfile \
     -t '$RUNTIME_IMAGE' \
     ."
```

该 Dockerfile 会从当前 build context 复制 `output/fe` 和 `output/be`。如果只重新编译了 BE，要先确认 `output/fe` 不是其他分支或历史版本的遗留产物。

### 8.2 启动专用 shared-nothing 集群

约定使用独立端口：

| 用途 | 容器端口 | macOS 端口 |
|---|---:|---:|
| FE HTTP | 8030 | 8330 |
| BE HTTP | 8040 | 8040 |
| MySQL Query | 9030 | 9330 |

启动命令：

```bash
ssh -F "$COLIMA_SSH_CONFIG" lima-colima \
  "docker run -d \
    --name '$RUNTIME_CONTAINER' \
    -p 127.0.0.1:8330:8030 \
    -p 127.0.0.1:8040:8040 \
    -p 127.0.0.1:9330:9030 \
    '$RUNTIME_IMAGE'"
```

首批功能测试使用容器自身的可写层，避免误挂旧集群数据卷。`docker stop`/`docker start` 同一个容器时数据仍保留；只有明确需要全新环境时才创建新的、名称不同的测试容器。

### 8.3 等待健康并检查服务

```bash
ssh -F "$COLIMA_SSH_CONFIG" lima-colima \
  "docker inspect '$RUNTIME_CONTAINER' \
   --format '{{.State.Status}} {{if .State.Health}}{{.State.Health.Status}}{{end}}'"
```

查看服务和最近日志：

```bash
ssh -F "$COLIMA_SSH_CONFIG" lima-colima \
  "docker exec '$RUNTIME_CONTAINER' supervisorctl status"

ssh -F "$COLIMA_SSH_CONFIG" lima-colima \
  "docker logs --tail 200 '$RUNTIME_CONTAINER'"
```

从 macOS 验证 BE 和 SQL：

```bash
curl --fail --silent --show-error \
  http://127.0.0.1:8040/api/health

mysql --connect-timeout=5 \
  -h127.0.0.1 -P9330 -uroot \
  -e 'select current_version(); show backends;'
```

只有容器状态为 `healthy`、BE `/api/health` 成功、`SHOW BACKENDS` 中 BE 为 Alive 后，才能开始 SQL+HTTP 用例。

### 8.4 停止专用集群

```bash
ssh -F "$COLIMA_SSH_CONFIG" lima-colima \
  "docker stop '$RUNTIME_CONTAINER'"
```

停止是可恢复操作，后续可以用以下命令继续：

```bash
ssh -F "$COLIMA_SSH_CONFIG" lima-colima \
  "docker start '$RUNTIME_CONTAINER'"
```

不要使用无名称过滤的批量删除命令。需要删除测试容器或数据时，必须先确认精确名称和是否仍需保留其中的测试数据。

## 9. SQL、HTTP 与 SQL Tester

### 9.1 手工入口

使用专项 HTTP 构建启动集群后，Tenant-TTL 请求发往 BE HTTP 端口：

```bash
curl --fail-with-body \
  -X POST \
  -H 'Content-Type: application/json' \
  --data-binary @request.json \
  http://127.0.0.1:8040/api/tenant_ttl_compaction/run
```

调用前通过 MySQL 创建测试专用数据库/表并产生目标 Rowset；调用后通过 SQL 查询业务结果，并检查 HTTP 返回的 coverage、source/output Rowset ID、处理版本和 `NOOP_VERIFIED`。

默认 Release 构建访问上述路径必须返回 404；不能只验证运行时配置关闭。

### 9.2 SQL Tester 配置

`test/conf/sr.conf` 当前没有填写集群地址。运行专用测试前配置测试集群：

```text
[cluster]
host = 127.0.0.1
port = 9330
user = root
password =
http_port = 8330
```

测试 helper 应通过 `SHOW TABLET`/`SHOW BACKENDS` 定位实际 BE，再调用 BE HTTP；不能把生产 Tablet、Rowset 或 Segment ID 写死在用例中。

All-in-One 会向 FE 上报 `127.0.0.1:8040` 作为 BE `MetaUrl`，因此从 macOS 运行该 helper 时，BE HTTP 必须像第 8.2 节那样同端口映射为 `8040:8040`。如果不能使用该宿主端口，则应把 SQL Tester 放到能直接访问 `SHOW TABLET` 返回的 `MetaUrl` 的容器/网络中运行，不应在 helper 中猜测或硬改 BE 地址。

安装一次 Python 依赖：

```bash
cd "$SR_ROOT/test"
python3 -m pip install -r requirements.txt
```

定向串行执行 Tenant-TTL SQL+HTTP 用例：

```bash
cd "$SR_ROOT/test"
python3 run.py \
  -d sql/test_tenant_ttl_compaction \
  -a sequential \
  -c 1 \
  -v \
  --skip_reruns
```

`sql/test_tenant_ttl_compaction` 已按仓库标准 T/R 目录落地，不是新增的独立 Python/Script runner。用例通过 `function: tenant_ttl_compact(...)` 调用 `test/lib/sr_sql_lib.py` 中的薄 helper，SQL 负责建表、分批写入和验数，helper 负责从 `SHOW TABLET` 发现 Tablet/BE 并请求特殊 HTTP 入口。首批用例使用串行模式，避免后台写入或其他 case 改变正在断言的 Rowset 数量和版本。

仓库中的同类参考包括 `test/sql/test_stream_load/T/test_stream_load_basic_txn` 的 `shell: curl` HTTP 步骤、`test/lib/sr_sql_lib.py::manual_compact` 的 Tablet 发现与普通 Compaction HTTP 调用，以及 `test/sql/test_sort_key/T/test_sort_key_dup_tbl` 的 `function: manual_compact(...)` 用法。

本轮实测结果：HTTP Action 独立 Release 目标 6/6 通过；上述 SQL Tester 命令运行 1 个串行 case，最终输出 `Ran 1 test ... OK`。若一次性本地集群因宿主共享磁盘使用率超过 95% 而拒绝建表/写入，应优先清理或更换测试磁盘。确需临时调高 `storage_usage_hard_limit_percent`/`storage_flood_stage_usage_percent` 时，只允许对明确命名的一次性测试集群操作，不得复用到生产或共享环境。

## 10. 每轮开发的最小验证顺序

每一轮按以下顺序收敛：

1. 检查 `git diff`，确认只修改本轮范围。
2. 对新增或修改的 C++ 文件运行 clang-format。
3. 运行对应的 Tenant-TTL 定向 ASAN 单测。
4. 扩大到直接依赖组件的 GTest suites。
5. 执行一次 BE Debug 增量编译，确保非测试目标可链接。
6. 涉及 HTTP 后，分别验证默认 OFF 构建和专项 ON 构建。
7. 涉及真实 Tablet 数据链路后，重新打包专用 all-in-one 镜像并运行 SQL+HTTP。
8. 首批收口时运行完整 `starrocks_test`、默认 Release 构建及 HTTP 符号/路由隔离检查。

任何测试失败都不能通过扩大重试次数或忽略失败来掩盖。应记录失败命令、HEAD、构建类型、容器镜像、GTest filter、日志和是否修改了 Tablet 数据。

## 11. 常见问题

### 11.1 macOS 上提示无法执行 `starrocks_be`

这是预期行为。二进制是 Linux ELF，必须在 Linux runtime/all-in-one 容器中运行。

### 11.2 宿主机找不到 CMake、Ninja 或 thirdparty

不要在 macOS 临时拼装另一套工具链。进入 `starrocks/dev-env-ubuntu:latest` 编译容器执行仓库脚本，保证与 StarRocks 的 Linux 构建环境一致。

### 11.3 修改编译宏后结果与预期不一致

先确认 `build.sh` 是否将 HTTP 测试开关显式传给 CMake。默认 OFF 和专项 ON 都必须显式配置，避免同一个 `be/build_Debug` 继承旧 cache。仍异常时再考虑针对该构建目录执行 `--clean`，不要删除其他构建或用户数据。

### 11.4 单测二进制存在但直接运行失败

优先改用 `run-be-ut.sh`，因为它会准备动态库、JVM、Hadoop classpath、测试数据和 Sanitizer 环境。

### 11.5 集群启动后 MySQL 暂时无法连接

all-in-one 会依次启动 FE、BE 并注册 BE。先等待容器 health 变为 `healthy`，再检查 `supervisorctl status`、容器日志和 `SHOW BACKENDS`，不要在启动过程中直接判定构建失败。
