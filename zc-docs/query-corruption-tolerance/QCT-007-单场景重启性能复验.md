## 2. 重置及核验范围

每组只启停已核验身份的本任务节点，清除进程内缓存/JIT/堆等历史状态；保留数据库数据，不重新导入。每组启动前、停止后计算所有测试 segment `.dat` 的文件名、长度及 SHA-256，要求完全一致；任何变化停止实验并保留证据，不覆盖文件。

同时核对 tablet/backend/version/schema、同一执行计划、二进制/源码/配置摘要、新 PID 与 start_ticks，确认没有复用上组进程。健康查询逐条校验行数 1000、Warning=0；不是逐条所有列完整值校验。OOM 历史计数为 2，要求无新增。

没有清理 OS 文件缓存、重启 VM 或清理编译缓存。因此本轮是**预热后的单场景稳态性能**，不是冷盘或冷启动测试。客户端和服务器仍共享容器 CPU 配额，不冒称三套独立硬件环境。

## 5. 解释边界

本轮一次只跑分页，不能直接把 QPS 与上一轮混合 SQL 的 QPS 比较，也不能用本轮代替混合负载或所有查询的验收。若单场景与混合场景表现不同，只能支持负载交互/状态影响的进一步调查，不能证明之前全部回退均由顺序造成。

前几个已完成子组的客户端接近使用一个 CPU 核，而服务器合计约 3.1 核。这提示客户端消费可能约束端到端吞吐，需结合服务端每查询 CPU 成本解释；不能把客户端饱和导致的版本差异缩小当作服务端没有开销。本轮保持固定客户端方法，不在观察结果后中途换客户端。

## 7. 如何解释这次实验

1. **此前较大的分页尾延迟回退没有在本轮稳定复现。** 新实验支持继续调查场景混合、运行状态和客户端交互，而不支持直接把以前全部差值计为容错代码的固定开销。
2. **不能单独归因于测试顺序。** 本轮同时改变了单 SQL / 混合负载、重启粒度、预热方式和采样量；没有做逐个变量切换的因果实验。旧结果依然有效地描述旧测试条件，不删除或改写。
3. **仍保留负面点估计。** ON 吞吐平均 -1.49%、P50 +3.29%，并非“所有指标零影响”。六块的探索性区间包含 0 只表示本设计下证据不足，不能证明等效性。
4. **客户端瓶颈值得优先排查。** 正式测量期间客户端约用 0.95～0.99 核，服务器约 3.00～3.18 核；客户端每查询 CPU 约 10 ms 与实际约 100 QPS 相吻合。ON 服务器每查询 CPU 点估计比 A 低约 0.68%，没有看到与吞吐下降相应的服务器 CPU 增加；但进程计数包含后台工作，不是容错函数专属 CPU，不能宣称代码优化收益。新实验尚未用多进程/JDBC 或独立资源客户端做对照，故只能将客户端瓶颈列为较强候选，不能最终定因。
5. **不替代混合负载或生产验收。** 本轮没有重跑 JOIN/全扫描/HTTP/页缓存 OFF、故障并发，也没有新增 JFR/perf/逐 SQL 服务端 Profile。不能将本轮分页结果推广到所有查询或 JDBC 服务。

若继续定位，优先保持相同 SQL、服务端资源和 A/B/C 顺序设计，增加能避免单 Python 进程消费上限的客户端对照，并同步采集服务端 Profile；之后再对原混合负载按组重启复验。上述下一步尚未执行。
