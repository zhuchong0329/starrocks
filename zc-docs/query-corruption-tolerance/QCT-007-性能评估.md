# QCT-007：最新代码性能复验

日期：2026-09-21。对象：`46ca14950dc76004c5df355ce2c975a77c50041a`，分支 `codex/query-corruption-tolerance`。用户本次明确授权性能验收，取代上一轮“等待后续命令”的状态；未修改生产代码、未新增提交或推送。

## 1. 结论

**正常、无损坏查询仍观测到局部吞吐和尾延迟回退，不能宣称最新代码完全没有性能下降。** 但也没有观察到所有负载普遍变慢。日志检索单请求的合并中位数较好，并发分页 P99 则仍需重点关注。

- 长预热、小 LIMIT/空结果/分页、Query Cache OFF、并发 1：两协议六种场景，C/ON 的合并 P50 比 A/社区基线低约 2.7%～6.5%。这只是本轮观测，不证明 QCT-007 的几处判断优化带来了同幅度收益。
- 同一日志检索混合负载，MySQL、并发 4、Query Cache OFF：C/A 吞吐第一轮 **+7.35%**，反向第二轮 **-5.19%**，方向不稳定。两轮合并分页 P99：A **75.024 ms**、B/OFF **83.653 ms**、C/ON **90.921 ms**；B/C 分别比 A 高 **11.50% / 21.19%**。不能用较好的 P50 掩盖这项尾延迟差异。
- 扫描/聚合/JOIN 等八类 SQL 的完整混合负载，MySQL、并发 4、Query Cache OFF：C/A 吞吐两轮分别 **-1.15% / -3.39%**，均有小幅回退；B/A 为 **+0.66% / -0.89%**。
- BE 页缓存 OFF 的首轮并发 C/A 吞吐约 **-15.23%**，全扫描 P99 为 **241.485 ms**，不能忽略。长预热反向复验为 **-1.49%**；另外两轮与首轮相同参数的正反复测为 **+0.06% / +2.63%**。因此 15% 的幅度没有稳定复现，但原始异常完整保留，不能直接断言它与代码无关。
- 故障并发首次发生一次健康连接的 MySQL 包序号错误；原样复跑通过。它不是健康性能矩阵中的失败，但意味着不能将本轮所有测试笼统描述为“一次全部通过”。详情见第 6 节。

性能测试与数据复核已完成。没有预设用户未批准的百分比通过线；若验收要求是“没有可见的 P99 回退”，当前证据不满足。按“尽可能小”的目标，建议下一步优先定位 MySQL 并发分页尾延迟及重启/重试协议异常，而不是继续凭判断次数推断性能。没有在本轮擅自实施优化或修复。

## 6. 故障并发：一次失败与一次原样成功复跑

仅对 `qct_faults.one_tablet`、tablet 10155 的已标记测试文件注入坏页，性能表 `qct_perf` 不参与注入。每阶段先预热 2,000 次，再测 1,000 条健康查询；中段并发一个故障请求线程，间隔至少 10 ms。沿用旧 helper、参数和断言，不修改生产代码或降低断言后“修成通过”。

首次 `interference-warm-r1` 的控制阶段通过，故障并发阶段在预热中失败，未取得该阶段有效样本：`Packet sequence number wrong - got 13 expected 1`。对应 10:40:46 UTC 的 FE 日志显示，健康 SQL 被 `CoordinatorMonitor` 以 backend 不存活取消，然后发生查询重试及连接关闭。证据支持与注入所需 BE 重启后的状态传播/取消时序有关，但没有做基线同故障对照或完成协议根因定位，不能断言它必然是测试工具问题、社区旧问题或与 QCT 无关。

finally 已恢复原文件、停止节点。保留 [失败阶段数据](qct007-performance-20260921/interference-r1/fault-concurrent.json)、[失败日志](qct007-performance-20260921/perf-interference.log)、[FE 对应日志](qct007-performance-20260921/interference-r1-fe-excerpt.log)，不混入健康 A/B/C 样本，不把首次控制阶段当作完整故障并发通过。
