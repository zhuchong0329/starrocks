# 本地 OLAP 查询文件损坏容错：技术设计

版本：v1.0，2026-09-19。需求已确认、编码已授权；实现和测试结果以每轮记录为准。
基线：9559176fab6e2cb885779f1e7b680133d58d6972。
配套：[需求文档](需求文档.md)、[实施规划](实施规划.md)。

## 1. 简化后的核心

本阶段只需要“本次是否容忍过损坏”这一单调标记，不再需要可用输入计数、逐输入健康矩阵、全部不可读判定或所有 BE 最终摘要屏障。标记只从 false 变为 true，不恢复，不控制其他任务调度。

正常执行仍使用原计划、缓存、并行度、JOIN/运行时过滤、EOS 和 LIMIT 取消。独立扫描允许的错误局部转为任务结束；此行为差异是容错功能本身，不授权新增完成依赖或确认等待。

全部独立输入损坏也按现有算子语义计算：明细可能零行，COUNT 可能为 0，外连接可能产生 NULL 补齐行，均附 Warning。

## 2. 分层职责

| 层 | 最小修改 |
| --- | --- |
| FE 用户查询入口 | 固化配置及资格；内部任务、写入、不支持源/路径不下发容错 |
| BE 独立 OlapChunkSource | 仅允许的存储 Corruption 标记查询、丢弃失败 Chunk、结束自己 |
| BE 查询上下文 | 单调损坏标记；无成功读证据、逐行统计、tablet 停止集合 |
| 现有 BE 数据传输 | 将有关标记搭载数据/结束消息，不增加消息或等待 |
| 现有根结果返回 | 携带最终标记，FE 不新增诊断屏障 |
| FE 会话及输出 | 聚合一个 Warning；MySQL 最终包、SHOW WARNINGS、HTTP 末尾字段 |

具体字段和类名以实现为准。协议使用新可选字段，旧请求缺省严格。

## 3. 原流程内传播：实现审查重点

基线状态报告和结果 EOS 不天然有序，所以不采用“给最终 Profile 增加字段然后等它到达”。此前 F1 全 BE 屏障、F2 异常登记确认后才 EOF 的候选均取消。

候选是在现有数据通道携带单调标记：

1. 本 BE 独立任务在转为 EOF 之前记录损坏。
2. 已有 Exchange 请求随数据/EOF 携带标记，接收方先合并标记再使该包数据/EOF 可见。
3. 标记不能像近似审计计数一样发送一次后清零：多个目的端、提前取消、增量统计采样都可能丢失它。损坏后应持续携带，或证明每个依赖通道都已收到。
4. 同 BE 片段可复用查询上下文；跨 BE 必须沿实际通道传播。
5. 根结果使用原有结果统计/结束消息返回标记，FE 原完成点消费，不等待其他 BE。
6. 纯 EOF、JOIN 构建侧零输出、广播/分区 Exchange、本地 passthrough、CTE、多输入和 LIMIT 需要分别测试。
7. 运行时过滤等控制路径可能越过数据依赖；未接入且不能证明可靠的路径保持严格执行，不能通过禁用优化来支持容错。
8. 不因 FE 暂未收到报告就假定无损坏；也不等待已经无关的后台取消/收尾。

上述是待代码验证的实现路径，不表示所有复杂计划已覆盖。开放容错前明确资格条件及未接入范围。

## 4. 扫描错误边界

仅在本地独立 Reader prepare/open/get_next 调用返回 Corruption 时转换。表达式、公共 prepare、共享队列拆分、rowset 固定等错误原样传播。

prepare 出错不能直接从 ScanOperator 顶层吞掉；该层也包含共享 try_get 错误。独立 Reader 未完成初始化时必须安全进入既有 EOF/资源释放路径，不允许空指针读和不完整 Chunk 入队。

读中出错先丢弃当前 Chunk，再返回任务结束；之前入队的成功 Chunk 不回滚。缓存 lane/owner、token 和活动任务计数沿现有生命周期结束，不终止整个 ScanOperator。

## 5. FE 资格与客户端

资格由用户只读 SELECT、实际本地扫描源、受支持 Pipeline 与结果协议共同确定。配置 false 时短路，不建立本功能集合/RPC。不能仅因为 TQueryType=SELECT 就给内部查询开启。

排除 outfile、写入、内部统计/维护、诊断执行、外部/lake、短路/非 Pipeline、HTTP raw、Arrow。标准 HTTP 在 QCT-005 才激活，前几轮产品入口不提前吞错。

MySQL 聚合 Warning、最终包计数、SHOW WARNINGS 会话快照以及转发路径保持一致。严格错误优先。JDBC 实际驱动联调，不通过新增结果列实现。

HTTP 只扩展标准 NDJSON 末尾 statistics 记录；关闭/不适用无额外字段。raw 严格。流中严格错误保持现有断连语义。

## 6. Query Cache 与范围限制

不改缓存策略或完整性，不用通用 PARTIAL 算子依赖传播实现第二阶段。单调标记仅服务本次诊断，不能保证历史缓存污染被后续查询识别。

未接入控制/数据路径不绕行、不强制切换计划，而是严格执行并列出限制。第一阶段并非全盘校验、持久隔离或副本修复。

## 7. 性能影响评估

用户已调整为“尽可能小的影响”，集中评估在编码完成后，零影响证明不再是启动门槛；保持现有执行流程仍是硬约束。

| 路径 | 预计新增工作与控制 |
| --- | --- |
| OFF | 一次查询级配置短路；无诊断 RPC、集合、扫描 I/O 或等待 |
| ON、健康 | 资格检查、必要的固定标记读取；不统计成功行、不逐 page 检查、不为诊断多读文件 |
| ON、损坏 | 标记更新、失败任务收尾、有界 Warning；不清零传播状态，不形成重试循环 |
| Exchange | 复用既有消息；必要的标记检查，损坏后少量控制字节，不新增往返 |
| MySQL | 最终 Warning 计数；仅有 Warning 才需要客户端读取详情 |
| HTTP | 每 SQL 末尾少量字段；不添加逐行字段 |
| 其他查询 | 诊断占用 CPU/网络/共享资源，需要故障并发测试 |

新增原子读取、字段布局、条件分支和序列化都不是物理零成本，不能用“不新增锁”或“不新增 RPC”宣称零回退。不要每 Chunk 更新共享成功计数；不新增等待、预校验 I/O、计划改写、缓存绕过或强制慢路径。

故障后继续完成查询与原版立即报错的工作量不同，分别衡量诊断成本、健康请求干扰和业务成功率。

QCT-006 对照 A=原版、B=新 OFF、C=新 ON。小 LIMIT、空结果、点查/短路、缓存命中、全扫描、冷热页缓存、多 BE JOIN、饱和并发均关注首行/完成时延、P99、吞吐、CPU/内存/RPC。保持硬件、编译参数、数据、计划一致；先报告噪声、原始样本和环境局限。发现明显回退要定位优化，不自行编造验收阈值或声称未测项目通过。
