## 2. 轮次与验收

### QCT-000：对齐记录

同步最新需求/设计/计划和隔离环境，提交文档。仅文档与环境确认，无功能或性能通过结论。

### QCT-001：配置、资格与可选协议

代码默认 false，查询快照、用户 SELECT/实际本地源/受支持结果路径资格；新增可选 query option 和最小单调损坏标记协议。产品入口暂不激活半成品。
建立隔离源码、Maven 和 C++ 构建缓存。

单测：缺省 false、开关、内部/写入/外部/lake/短路/混合源/未接入入口排除；协议生成及编译。验收记录实际执行结果，构建问题不混成业务修复。

### QCT-002：独立扫描任务容错

只在独立本地存储初始化和 get_next 错误分支接入。失败 Chunk 丢弃，任务 EOF 安全收尾，同 tablet 其他任务继续。无成功证据统计。

单测：首读、读中、初始化损坏、半填充 Chunk、开关 false、非 Corruption、共享错误不吞、取消、重复调用与资源释放。检查缓存 lane/owner 完成稳定性，不改缓存正确性。

### QCT-003：既有通道中的单调标记

把损坏标记接入查询上下文、现有数据/EOF 传输与根结果统计。不能只靠近似审计采样或可清零的增量计数；无需精确失败数。不新增 RPC/确认/等待。

单测：多目的端、重复消息、sticky OR、纯 EOF、零输出 JOIN、同 BE/跨 BE、LIMIT 与取消；未接入控制路径的资格排除。全部不可读依现有算子得到空/聚合结果并标记。产品入口仍未开放。

### QCT-004：MySQL/JDBC

接通用户 MySQL 入口，最终 EOF/OK Warning 计数、会话快照、SHOW WARNINGS、FE 转发。严格错误不覆盖。

单测及确认：诊断保留/清理、SHOW WARNINGS 本身不清空、LIMIT、prepared/text、连接复用；实际 Connector/J getWarnings 集成。无新列或额外结果集，健康查询无需额外请求。

### QCT-005：HTTP SQL

标准 NDJSON 末尾增加 partial_result/warnings，沿原有输出/完成时序；raw、OFF、不适用保持原语义和格式。

单测及确认：正常/部分/全部损坏、零行、严格错误、响应截断、keep-alive、raw 排除、客户端断开。与 MySQL 同一诊断来源。

### QCT-006：集中故障、性能评估和配置交付

真实 page checksum / magic / footer 故障只注入本任务测试数据，不操作 RAID。多 BE、JOIN、同 tablet 多任务、LIMIT、开关、缓存开关、公共/共享错误回归。覆盖声明与实际验证一致。

编码后进行 A/B/C 性能评估，关注小 LIMIT/空结果/P99/并发；报告原始数据、环境限制和可定位成本，不承诺零影响、不伪造未测结果。

验收后产品 conf/fe.conf 设置 true，代码默认仍 false。提供部署、Warning/HTTP 消费、已知缓存风险、未接入路径和关闭回退说明。保留所有构建/测试资产。

### 4.2 持久化布局

全部在新卷内，建议：

```text
/query-corruption-workspace/
  src/                       独立源码及独立 Git 元数据
    be/build_Release/        生产 Release
    be/ut_build_Release/     首选独立 UT 构建
    be/ut_build_Debug/       按需建立，不能与 Release 混用
    be/ut_build_ASAN/        按需建立，不能与普通 UT 混用
    be/ut_build_UBSAN/       按需建立
    output/                 保留可复用构建产物
  cache/ccache/
  cache/maven/
  logs/QCT-NNN/
  runtime/                   本功能运行包，不链接 TTL 包
  test-data/                 仅本功能的故障注入数据
```

宿主 worktree 的 `.git` 是指向主仓库元数据的文件，不能简单复制进容器当成独立可用 Git 仓库。首轮建议通过本功能分支的 Git bundle 初始化卷内独立副本，再同步本轮修改；不挂载 Tenant-TTL 缓存、不将 `.git` 链接到 TTL 工作目录。必须记录实际源码提交及未提交修改清单，不能让新产物显示为 Tenant-TTL 版本。

之后只同步实际变更源码/明确新增文件；删除的源码逐项处理，禁止全目录删除式同步。Maven 下载和 ccache 均使用新卷路径；不依赖容器可写层保存长期构建资产。

### 4.3 构建纪律

- 首轮检查依赖、架构、GCC/链接器、Release/UT 配置；固定后后续增量复用。
- 生产与 UT 分目录，执行前检查 CMakeCache/编译参数，而非仅看目录名。
- 先用保守并行度，结合当时内存使用调整；6 CPU/16 GiB 是容器上限，不是要求始终占满。
- FE 测试/打包前检查 POM 和脚本是否隐式 clean；使用支持的跳过 clean 参数，避免损毁增量状态。不得未经核验承诺任一命令一定不清理。
- 每轮记录构建命令、环境、源码 SHA、测试范围、结果和未测原因；输出日志保存在新卷。
- 本次 178 GiB 可用量允许开始独立构建准备，但不能保证同时容纳所有 sanitizer 构建与大量测试数据。首次全量构建、新增构建类型、故障注入前都重查空间。
- 建议保留至少 30 GiB 操作余量。若预计新增构建占用加余量超过可用量，暂停并与用户对齐；不得清理旧卷或擅自再次扩容。
- 只允许一个容器写本功能构建树。不同功能的编译即使卷隔离，也共享 VM 资源，不主动打断其他任务来抢内存。
