# 查询文件损坏容错：部署与客户端接入

适用基线：本地社区 4.0.11 / `9559176fab6e2cb885779f1e7b680133d58d6972`。
第一阶段实现及本地验收已完成；实际覆盖、性能回退和未测范围以 [QCT-006 验收](QCT-006-验收.md)及[性能报告](QCT-006-性能评估.md)为准，不承诺零开销或生产 SLO。

## 1. 开关与升级顺序

这是 **FE 启动配置**，不是 SQL session variable，也不承诺 ADMIN SET FRONTEND CONFIG 热更新。
Java 代码缺省 `false`；产品默认配置文件 `conf/fe.conf` 已增加：

```properties
enable_query_corruption_tolerance = true
```

已有部署须修改每台 FE 实际使用的配置文件并按正常维护流程重启 FE。只修改源码仓库的模板不会自动改变已部署实例。各 FE 配置应一致，避免入口不同导致行为不同。

每条查询使用执行开始时取得的配置快照，不会在运行中切换错误语义；但本阶段配置变更需要重启 FE，因此仍应安排在途查询和连接的排空/维护。不能把“只对新查询下发新值”理解为承诺无中断热切换。

滚动升级期间必须保持 `false`。先完成所有 BE 和 FE 升级，再启用。可选 Thrift/Protobuf 字段能保证旧请求缺省严格、旧节点能够解码，但**不代表新旧 BE 混跑时能够可靠传递 Warning**：旧中间 BE 可能丢弃它不认识的诊断字段。本阶段未实现跨版本功能协商。

配置在每条受支持查询开始执行前读取并下发，不修改该查询的计划、并行度或缓存选择。用户查询以外的内部任务不会因为 FE 开关为 true 自动获得容错能力。

## 2. 实际适用范围

- 用户只读 SELECT；实际扫描源全部是本地 shared-nothing OLAP 表。
- Pipeline 独立扫描任务中的存储 Reader `prepare/open/get_next` 返回明确 `Status::Corruption`。
- 支持 MySQL 文本查询、JDBC text/server-prepared，以及标准 HTTP SQL NDJSON 路径。
- 当前失败 Chunk 整体丢弃；该独立任务剩余范围停止；之前成功输出的数据保留。同 tablet 的其他任务继续独立执行。
- 全部独立任务不可读也允许成功 + Warning；明细可能零行，聚合可能产生 COUNT=0，外连接可能产生 NULL 补齐行。

不容错的路径仍按原来方式运行并报错，不为支持容错而改走慢路径：公共扫描准备、共享 morsel 拆分/索引加载、非 Pipeline、短路、Arrow、HTTP raw、混合外部表/lake，以及存在跨节点运行时过滤控制依赖的计划。JOIN 不一律排除，但含远端 runtime filter 的 JOIN 保持严格。

版本缺失、普通文件缺失、一般 I/O、权限、网络、OOM、取消、超时和表达式错误不会被 Warning 替代。写入、导入、导出、内部统计、物化视图刷新、compaction、clone、checksum 均不在本功能范围内。

本功能不修复文件、不标记 BAD、不切换副本，也不是全盘巡检。没有 Warning 仅表示本次最终响应未包含被容忍的损坏，不是文件健康认证。未读取的列/范围、提前 LIMIT 取消、缓存命中都不能用于判断物理数据完整性。

## 3. MySQL 与 JDBC

成功结果的最终结束包包含 Warning 数量。当前每条 SQL 最多聚合一条本功能 Warning：

| 字段 | 值 |
| --- | --- |
| Level | `Warning` |
| Code | `9000` |
| Message 前缀 | `SR_QUERY_PARTIAL_RESULT` |
| 含义 | 结果可能不完整或不准确；包含 query_id，不暴露文件路径 |

MySQL 客户端可在同一连接立即执行 `SHOW WARNINGS`，也支持 `SHOW WARNINGS LIMIT ...`。不要先执行其他普通 SQL；它会清除上一条查询的诊断。读取 `SHOW WARNINGS` 本身不会提前清空诊断。

JDBC 消费顺序示意：

```java
try (Connection connection = dataSource.getConnection();
     Statement statement = connection.createStatement()) {
    try (ResultSet result = statement.executeQuery(sql)) {
        while (result.next()) {
            consumeRow(result);
        }
    }
    // 完整消费结果后、执行下一条 SQL/关闭 Statement/归还连接池之前读取一次。
    SQLWarning warning = statement.getWarnings();
    boolean partial = false;
    for (SQLWarning item = warning; item != null; item = item.getNextWarning()) {
        if (item.getErrorCode() == 9000
                && item.getMessage().contains("SR_QUERY_PARTIAL_RESULT")) {
            partial = true;
            recordWarning(item.getMessage());
        }
    }
    finishResponse(partial);
}
```

`consumeRow/recordWarning/finishResponse` 为产品接口示意，不是新增的 JDBC API。
结果行中不增加 `partial` 列；产品检索服务可在自身响应对象中增加 `partialResult` 与提示文案，页面据此展示。不新增第二个 SELECT 结果集。

异常仍按 `SQLException` 处理，不能把“先收到了几行”当作成功。建议保存一次 `getWarnings()` 返回值再遍历，不依赖不同驱动对重复读取 Warning 的行为一致。QCT-004 为协议层联调；[QCT-006](QCT-006-验收.md) 另记录 Connector/J 8.4.0、MariaDB Connector/J 3.3.2 的真实 BE 文件损坏 text/server-prepared 验证。

健康查询不要求产品额外发送 `SHOW WARNINGS`。驱动可依据结束包的 Warning 计数，在需要读取详情时取得诊断；这是异常结果消费，不是 FE/BE 新增的查询完成屏障。

## 4. HTTP SQL

标准入口仍为 `/api/v1/catalogs/default_catalog/sql`（也可使用既有带 database 的路由）。请求、用户列、meta 和 data 记录不变；只扩展现有末尾 statistics 记录：

```json
{"statistics":{"scanRows":0,"scanBytes":0,"returnRows":0},"partial_result":true,"warnings":[{"code":"SR_QUERY_PARTIAL_RESULT","message":"SR_QUERY_PARTIAL_RESULT: result may be incomplete or inaccurate ... query_id=..."}]}
```

实际启用且未容忍损坏时：`partial_result=false`，`warnings=[]`。
关闭或不适用时不增加这两个字段。`onlyOutputResultRaw=true` 保持严格且不增加末尾统计记录。

4.0.11 基线的 raw 标志保存在连接上下文中，请求只在 true 时设置，没有相应的 false 重置；本功能不混入这项独立社区问题的修复。因此不要在同一 HTTP keep-alive 连接混用 raw 与标准模式；用新连接恢复标准模式。

客户端必须完整读取 NDJSON，并确认收到最终 statistics 和 HTTP 正常结束。HTTP 200 只是响应头已发出，不保证后续查询成功：共享阶段或其他严格错误发生在发送后时，沿基线行为关闭连接，不伪造成功末尾记录。流中断、超时或缺失末尾记录应视为失败，而非 `partial_result=false`。

产品接口可直接把 `partial_result` 转为自己的显式字段，页面显示“部分数据因文件损坏未参与查询，结果可能不完整或不准确”。不能解释为精确丢失行数，也不能保证 JOIN/聚合结果只是正确结果的子集。

## 5. Query Cache 风险与回退

第一阶段不修改 Query Cache：部分结果可能写入缓存，后续命中时可能没有 Warning。即使关闭本开关，历史不完整缓存值也不会自动恢复。基线 `enable_query_cache` 默认 false，但应检查实际会话和部署设置。

关闭功能：将各 FE 配置改为 `false` 并按正常维护流程重启使其生效。注意重启对在途查询/连接的影响；之后的新查询恢复严格读取，但关闭不是副本修复或缓存清理。若需对历史缓存做运维处理，应另行核实、授权，不由本功能自动清空。

第二阶段 B 方案再处理缓存完整性传播与写入保护。第一阶段不要对客户声称已经解决此问题。

## 6. 定位与环境隔离

客户端 Warning 的 query_id 可关联 BE 日志中的 `independent scan stopped after tolerated file corruption`，其中保留 tablet_id 和原始错误详情。日志仅在容错分支产生，不为健康读取新增逐行/逐页日志。

测试与编译仅使用 QCT worktree、容器 `starrocks-query-corruption-4.0-build` 和持久卷 `sr-query-corruption-4.0-build-cache-arm64`。不得借用 Tenant-TTL 缓存或对其数据注入故障；具体路径见仓库 `AGENTS.md`。
