# QCT-006：性能评估与适用限制

完成日期：2026-09-20（本文日志时间另明确标注 UTC）。配套：[设计](设计文档.md)、[验收](QCT-006-验收.md)。

## 1. 结论先行

功能没有新增诊断等待、RPC 往返、读盘校验、逐行完整性统计或计划回退。**这不等于零开销，也不等于所有负载无性能回退。**

长预热的重点查询对照中，Query Cache 关闭、并发 1 时，ON 相对原版的完成时间中位数增加约 **0.058～0.222 ms（约 0.9%～2.5%）**；这是所列六种场景的观测值，不是所有场景的上界。部分并发场景吞吐与 P99 有可见回退，例如重点 MySQL 混合负载在并发 4、Query Cache 关闭时，两轮 ON 吞吐分别比原版低约 **3.4%、7.1%**，合并明细分页 P99 从 **76.469 ms** 增至 **87.204 ms**。

这些差异没有被隐藏或全部归为噪声。反向复测、资源检查及 FE CPU 采样没有发现新增等待或重型资格判断；剩余差异不能从本次共享虚拟机实验中严格拆分为容错指令、JIT、调度、客户端和环境扰动各自的成本。当前方案已采用小范围错误分支与既有通道传播，性能评估完成，**不作零回退承诺或生产 SLO 认证**。如生产对某一延迟/吞吐有硬门槛，应使用实际数据、并发与机器再验收，不能用本报告替代。

## 3. 长预热重点查询：单请求完成时延

以下均为 BE 页缓存 ON、Query Cache OFF、并发 1；两轮合并每用例/版本 1,000 个有效样本，单位 ms，单元格为 **P50 / P99**。合并样本不冒充更多独立轮次。

| 协议 / 查询 | A 原版 | B OFF | C ON |
| --- | ---: | ---: | ---: |
| MySQL LIMIT 10 | 5.813 / 8.143 | 5.634 / 8.099 | 5.958 / 8.988 |
| MySQL 空结果 | 6.713 / 9.430 | 6.449 / 9.211 | 6.771 / 10.857 |
| MySQL 倒序 LIMIT 1000 | 15.801 / 24.979 | 15.456 / 21.001 | 16.023 / 24.307 |
| HTTP LIMIT 10 | 4.501 / 6.167 | 4.603 / 6.371 | 4.608 / 6.357 |
| HTTP 空结果 | 4.983 / 6.672 | 5.075 / 6.930 | 5.085 / 6.918 |
| HTTP 倒序 LIMIT 1000 | 15.246 / 18.962 | 15.458 / 19.556 | 15.460 / 19.853 |

首行 P50：MySQL LIMIT 10 为 5.763 / 5.592 / 5.905 ms，HTTP LIMIT 10 为 4.243 / 4.344 / 4.361 ms；MySQL 明细页为 12.249 / 11.896 / 12.399 ms，HTTP 明细页为 11.268 / 11.386 / 11.446 ms（顺序均 A/B/C）。没有把完整传输 1,000 行的时间混称为首行时间。

不能只看中位数：MySQL 空结果 P99 观测增加 1.427 ms，LIMIT 10 增加 0.845 ms。它们不是额外等待所有 BE 诊断的结果——实现中不存在这一完成屏障——但本次测量也不能证明这些尾部差异全部来自环境。

Query Cache ON 的同类单请求中，MySQL 的 ON 中位数没有比原版更慢；HTTP ON 的中位数增加约 0.114～0.325 ms。由于这些重点 SQL 并未命中 Query Cache，不能解释成缓存正确性或缓存性能的改善/退化。

## 4. 并发与吞吐：保留逐轮数据

以下为 focused 重点混合负载，并发 4。单元格为 **第 1 轮 / 第 2 轮 QPS**，不是把不同工作负载混合计算吞吐。

| 协议 / Query Cache 开关 | A 原版 | B OFF | C ON |
| --- | ---: | ---: | ---: |
| MySQL / OFF | 275.53 / 279.52 | 274.91 / 265.77 | 266.29 / 259.78 |
| MySQL / ON | 287.78 / 283.27 | 285.18 / 284.02 | 289.92 / 293.39 |
| HTTP / OFF | 288.18 / 286.92 | 284.01 / 292.46 | 282.31 / 283.25 |
| HTTP / ON | 284.23 / 286.45 | 296.39 / 284.87 | 291.39 / 281.67 |

MySQL / OFF 的 ON 明细页 P50/P99 为 23.861/87.204 ms，对应原版 23.137/76.469 ms；这项回退必须保留。MySQL / ON 的明细页 P99 则是 ON 74.748 ms、原版 79.021 ms，因此不是所有子组都出现相同方向变化。

包含扫描/聚合/JOIN 的主矩阵在 MySQL 并发 4 下平均服务器 CPU 达约 5.67～5.84 核，接近 6 核容器配额。重点矩阵平均服务器 CPU 较低，另有客户端开销和短时限流；不能把所有差异都简单归因于“CPU 满载”。例如 focused-r2 MySQL/OFF/C 的 330 个配额周期中 39 个发生限流，累计 throttled 约 0.706 s；A 为 310 周期中 37 个、约 0.485 s。CPU 计数包含预热与后台活动，不是精确单 SQL CPU。

主矩阵四个服务器进程的结束 RSS 合计约 2.45～2.98 GiB，重点矩阵约 2.29～3.01 GiB；它们包含 JVM/缓存预热，不用于宣称严格无泄漏。没有新增 OOM；历史两次 OOM 是早期构建和已修复测试夹具问题，均另保留记录。

## 6. 故障并发和热点排查

首组故障并发观察存在明显预热趋势，见验收记录；又执行 `interference-warm-r1`，每阶段先预热 2,000 次，再记录 1,000 条健康请求。中段并发 977 条故障请求（含该阶段预热，单线程、间隔至少 10 ms）。健康请求全部正确且没有串入 Warning，三个阶段 P50/P99 为：

| 阶段 | 健康 P50 / P99，ms |
| --- | ---: |
| 故障流前 | 5.033 / 7.305 |
| 并发故障流 | 3.806 / 4.870 |
| 故障流后 | 3.980 / 5.555 |

仍有预热/运行顺序影响，**不能把并发阶段更快解释成故障没有资源代价**。这证明的是本次有界负载下仍能正确服务健康查询、无诊断串扰；不是任意损坏规模的吞吐保证或长期无泄漏证明。

为排查资格检查重操作，另在专用 C FE 使用 JDK 17 JFR：`fe-profile-c-on`，12,000 条有效健康查询，计时数据明确排除在上述对照之外。1,277 个 ExecutionSample 未采到 QueryCorruptionPolicy/Warning 栈，主要可见解析、集合、规划和 Thrift 等通用路径。采样分辨率有限且没有配套原版 JFR，不能据此精确分摊几微秒开销或证明零成本；本次未发现值得用新增计划/等待机制替换的重型资格判断。

## 7. 尚未覆盖与交付边界

- 不清空 VM/宿主 OS 缓存；进程重启不是实际冷盘。不把 BE 页缓存 OFF 称作 OS 冷缓存。
- 单开发虚拟机、容器内网络、固定小规模合成数据、两个主要重复轮次；未测生产 x86、多机网络、长稳压力或所有复杂查询。
- 没有预设用户未批准的百分比通过线。阶段一性能评估完成，但观测回退不被改写成“无影响”；生产 SLO 另以真实负载约束。
- 部分结果的 Query Cache 污染/后续漏标仍是用户明确接受的第一阶段限制，没有借性能验收修改缓存策略。
- 所有原始数据、失败记录、剖析文件、编译缓存和恢复备份保留；没有清理或占用 Tenant-TTL 编译资产。
