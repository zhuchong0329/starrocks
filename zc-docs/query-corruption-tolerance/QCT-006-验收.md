### 2.1 数据、文件与证据

实际执行时间 2026-09-19 14:14–14:38 UTC。专用集群位于 `/query-corruption-workspace/runtime/qct-cluster`，BackendId 10002/10003/10004。所有文件注入发生在 replication=1 的 `qct_faults` 测试表，不是用户数据或 `_statistics_` 表。

- `one_tablet`：tablet 10155 / BE 10002，共 32,768 行。`k` 列实际数据页起始 ordinal 为 0/8192/16384/24576，对应文件 offset 0/375/819/1297；通过本次生产 BE 的 `meta_tool --operation=show_segment_footer` 和只读页定位工具取得，不猜偏移。分别修改 offset 0、1297 触发 checksum mismatch。
- `multiple_tablets`：6 个 tablet 共 32,768 行；只损坏 BE 10003 的 tablet 10163。Profile 记录 19401/19501/19601 三个实际扫描地址，最终 MySQL/HTTP 均返回 27,267 行。`profile-multiple-tablets.txt`、`physical-multiple-{mysql,http}.json` 保留计划、统计、Warning/query ID。
- 首次 LEFT JOIN 被优化器重排为 RIGHT OUTER JOIN，不能单独证明“损坏构建侧远端 EOF”。后续已通过测试 SQL hint 固定输入顺序，分别验证 broadcast/shuffle 的 LEFT/INNER，Profile 均出现 19401/19501/19601 三个地址与对应 HASH_JOIN_BUILD，补齐了这一排列；没有修改产品优化器行为。
- 独立扫描测试会话关闭内部拆分；并行测试单独打开 force_split，并将测试 BE 的 `tablet_internal_parallel_max_splitted_scan_rows` 临时设为 16,384。对应 `profile-same-tablet-split.txt` 证明两个实际任务。该动态配置在 BE 重启后恢复默认，没有带入性能环境。
- 首 page、后 page、magic/footer 的原文件和故障摘要、字节位置、inode、完整备份均保留在专属 `test-data/qct-backups`。恢复汇总在 `physical-restoration-build-resume.log`；所有清单逐个匹配原 SHA-256，恢复后的完整明细查询也通过。

BE 日志实际出现 `Corruption: Bad page: checksum mismatch`、`magic number not match`、`failed to parse footer`。ON 独立路径另有 `independent scan stopped after tolerated file corruption` 和 query/tablet ID；OFF/共享路径为原扫描/Driver 的 Corruption。没有模拟 BE 状态来代替本节物理验证。

所有本节证据位于专属卷 `logs/QCT-006`。JSON 内保留实际 SQL、设置、计划、返回行数、前 16 行、顺序摘要、最终 Warning 或 HTTP 统计记录；Profile 是查询结束后另行读取，未增加执行阶段屏障。

### 2.2 客户端与生命周期

真实客户端为 PyMySQL 1.1.1、Connector/J 8.4.0、MariaDB Connector/J 3.3.2。两种 JDBC 各测 text/server-prepared：ON 实际坏页返回 0 行、两列不变、一个码 9000 的 `SR_QUERY_PARTIAL_RESULT`；健康请求无 Warning；OFF 坏页返回原 SQLException。分别见 `physical-jdbc-page-first.log` 和 `physical-off-jdbc.log`。这里不再只是前几轮的模拟 BE 联调。

MySQL 同连接连续两次 SHOW WARNINGS 不消费诊断，SHOW ERRORS 不展示本 Warning；后继健康 SQL 不继承。HTTP keep-alive 使用相同 connectionId，部分请求末尾 `partial_result=true`，健康后继为 false/空 warnings；OFF 末尾没有新字段。raw/共享/OFF 故障在输出 meta 后关闭响应，没有正常结束和 statistics，保留了基线语义。

后段坏页连续 30 次故障明细读取，各返回 24,576 行；每次随后健康请求均返回 8 行且没有遗留 Warning，见 `physical-cancel-repeat-v2.jsonl`。这是有界重复回归，不作为长稳资源无泄漏证明。

### 2.3 测试过程中的失败与未覆盖项

- 首次 fixture 导入把 SQL 许可证注释中的分号误当分隔符，在任何建表前失败；去掉整行注释后成功。未重复导入或删除数据，失败日志 `cluster-init.log` 保留。
- 首次客户端断连脚本在已关 socket 上退出 SSCursor 上下文，触发客户端清理异常；改用独立客户端进程在读取 10 行后退出，重复回归通过。原 `physical-limit-cancel-repeat.jsonl` 的 30 次 LIMIT 结果仍保留，但不把其整体记为通过。
- 首两次“远端过滤”用例未实际生成远端过滤（小表阈值/本地过滤），因此查询容错成功而测试严格断言失败。之后测试 SQL 显式使用 shuffle、关闭重排，并设置测试会话 `global_runtime_filter_probe_min_size=0`，`physical-remote-filter-strict-v3.json` 严格回归通过。没有为这些测试改变产品查询计划。
- 非 Pipeline 查询在该 4.0.11 基线直接报“不再支持 non-pipeline engine”，不是物理 Corruption。保留 `physical-non-pipeline-strict.json` 的断言失败，不称其为真实非 Pipeline 文件损坏覆盖；资格排除另有 FE 单测。
- 尚未跑真正双 FE 转发拓扑、全 BE UT、ASAN/TSAN、全部表模型/所有复杂 CTE/控制依赖排列或生产长期压力。FE 转发为 mock 回归；真实存储主场景为 Duplicate Key 明细，Primary Key 仅作健康短路性能/计划对照。不能将这些限制写成已验证。

### 2.4 补充真实故障回归

`physical-supplement-r2` 于 2026-09-19 16:58:46 UTC 全部通过；所有清单匹配恢复后的原始 SHA-256，完整明细恢复为 32,768 行，四节点停止。原 `physical-supplement-r1` 在注入前因工具把 SHOW TABLET 的文本 ID 与整数比较而失败，没有修改文件；修正并新增单测后重新完整执行。

- 损坏 B 构建侧固定不重排：A 使用分布在三 BE 的 `multiple_tablets`，B 为坏 `one_tablet`，筛选 A.k<=8。broadcast 和 shuffle 两种分布的 LEFT 都返回 8 行、B 列为 NULL，INNER 都返回零行；全部 Warning=1。详细 SQL、EXPLAIN 和各实例 Profile 均保存。
- 复用 CTE 的 UNION ALL：实际 MultiCastDataSinks，零行+Warning；当前实际放置在 BE 10002，不把它写成跨 BE CTE 验证。
- Connector/J 8.4.0、MariaDB Connector/J 3.3.2：真正的 server-prepared `where k > ?`，绑定 0，均返回零行、两列不变、Warning=9000；不再只依赖无参数 prepared。
- `message` 列第二页实际 ordinal=421、offset=5824。读 `k,message` 返回零行+Warning，没有泄漏失败 Chunk 内已读的前 421 行；只读 `k` 返回完整 32,768 行、没有 Warning，验证未加入额外列完整性扫描。
- 独立 Reader 初始化遇 magic 损坏，显式开启 Query Cache 的 `k%8,count(*)` 聚合仍能结束并传回 Warning；只验完成性，不保证缓存内容正确。
- 三个各 1,000 次健康请求阶段全部正确且无 Warning；中间阶段并发 405 条被容忍的故障查询（单线程、间隔至少 10 ms），没有跨查询诊断污染。健康 P50/P99 依次为 7.567/13.102、5.401/8.954、4.796/10.320 ms。存在明显预热趋势，不能把中间阶段更快解释为“故障无性能代价”；这组只提供有界干扰观察，不作因果性能结论。

物理功能回归没有要求变更生产实现。随后 `interference-warm-r1` 每阶段增加至 2,000 次预热、1,000 个有效健康样本，中间并发 977 条故障查询（含预热）；健康结果全部正确且无 Warning。仍有预热/顺序趋势，见性能报告，不据此宣称零干扰。所有故障清单恢复原始 SHA，完整明细的最终摘要仍为 `c91ff23369051ae01ed075351730e75b2373010f3d6ad2ab8176f7ad12aa046f`。

## 3. 性能评估（完成，存在非零代价）

保留原始样本、计划、二进制/配置摘要和运行身份；工具在采样前检查 A/B/C 标签与四个节点启动记录一致。并发吞吐用实际采样墙钟窗口，不能用时延相加冒充。OS 缓存、共享 VM 噪声和有限 P99 样本须公开；不清空整台 VM 缓存、不影响 Tenant-TTL。

进程重启首轮 `process-restart-r2` 已完成 A/B/C，每版本每用例 1 个样本，无预热、关闭 BE 页缓存；不是 OS 冷缓存。四类查询 EXPLAIN 摘要均一致。该单样本不用于稳定分位数或性能通过结论。
