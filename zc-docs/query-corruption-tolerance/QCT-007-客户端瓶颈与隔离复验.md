# QCT-007：客户端瓶颈与 CPU 隔离复验

日期：2026-09-22。**状态：两部分均已完成，30 组 / 300,000 正式请求，另有 219,910 条预热样本；原始数据审计通过。** 四个测试节点和独立客户端均已停止，无新增 OOM。原 CPU 有效执行范围已恢复，但 Docker 配置保留显式 `0-7` 而不是原空值，详见第 6 节。

结论：原单进程四线程客户端确实显著限制了本分页测试。原共享环境换四进程后，吞吐 +74.05%、P99 -49.66%；CPU 隔离条件下仍复现吞吐 +32.53%、P99 -29.01%。统一多进程、独立 CPU 后，六块配对 ON/社区吞吐 -0.068%、P99 +4.62%（约 +2.02 ms）。平均吞吐基本一致，但逐轮差异大、探索性区间宽，不能宣称零成本、严格等效或所有尾延迟无回退。

用户批准先检验单进程 Python 客户端是否约束分页测试，再排除客户端与服务端共享配额的影响。本轮只新增实验编排和证据，不修改生产实现、不重新编译、不更新 patch、不提交推送、不操作 Tenant-TTL。

## 1. 固定负载与对照原则

```sql
select k, message from qct_perf.events order by k desc limit 1000;
```

- 健康的 100 万行 Duplicate Key 日志明细、6 tablet、3 BE；不注入损坏。
- MySQL 文本协议、PyMySQL 1.1.1、SSCursor，每个连接完整消费 1000 行及结束包，逐请求核验行数及 Warning=0。
- 总连接数和 SQL 并发始终为 4；每个连接同步串行发 SQL。不是固定到达率测试，也不是最大容量搜索。
- 原 `tools/query_corruption/benchmark.py` 的 `execute/configure/check_healthy_sample` 原样复用。没有改成 COUNT、减少列/返回行数、提前停止消费、逐行打印或哈希。
- Pipeline DOP=2、Query Cache OFF、BE 页缓存 ON；不清 OS 文件缓存。
- 每组新的 FE/三个 BE/客户端进程；心跳稳定检查后，四个工作线程/进程全部建连，再共同预热 60 秒，每个工作者正式执行 2500 次，合计 10000 次。
- 记录实际计划、tablet/backend/version/schema、生产源码/产物摘要、进程身份、每条首行/完成时间和 CPU。每组前后校验全部测试 segment 文件摘要；不重新导入或覆盖数据。
- 所有工作者测量结束且资源快照完成后才写样本文件；多进程不在每次请求后向父进程传送结果。
- QPS 使用 `perf_counter_ns` 的单调时钟窗口计算；UTC 仅用于定位日志。开发 VM 的 UTC 可能校时，CPU 核数估计使用单调窗口，CPU/查询使用实际进程累计 CPU 差值。工作者另记录 `thread_time_ns` 两个边界，避免漏计子进程或把四个同 PID 线程重复计算四次。

## 2. 第一部分：只改变客户端进程模型

仅社区基线 `9559176fab6e2cb885779f1e7b680133d58d6972`。

- T：1 个 Python 进程、4 个工作线程。
- P：4 个 Python 工作进程、每进程 1 个工作线程；父进程只做编排。
- 仍共享 QCT 原容器 6 CPU / 16 GiB；不在本阶段改变资源分配。
- 四对顺序预先固定为 TP、PT、PT、TP，共 8 组，80,000 正式样本。
- 每对内比较，不把当天绝对 QPS 与前一天直接相除来计算客户端收益，不按结果挑选组或删除慢请求。

证据：专属卷 `logs/QCT-007/client-architecture-20260922-r1/`；脚本 `client-perf-20260922.py`，主日志 `client-perf-20260922-r1.log`。07:49:34～08:14:15 UTC 已完成 8 组、80,000 正式样本；只读重算通过。32 个不同服务端进程身份、8 个不同客户端父进程，所有计划/放置/产物摘要一致，21 个 segment 摘要未变，四节点停止且无新增 OOM。

服务端在 P 组达到约 5.25～5.32 核，加客户端约 0.65 核，接近共享的 6 核预算。四个 P 组 cgroup 累计限流时间增量分别为 8.580/7.192/9.781/3.744 秒；该计数不是直接可加到单条查询上的延迟。需要下一部分隔离配额，不能把本阶段 150 QPS 当作服务端最大容量。

## 3. 第二部分：独立客户端 CPU 后复验（已完成）

第一部分的多进程组接近共享的 6 核配额，出现限流；因此不能只换多进程就宣称已消除所有客户端/资源影响。以相同服务端 6 CPU 预算完成下列实验，每组预检和测量快照都验证 CPU 集合与配额：

- QCT 服务端容器固定 CPU 集合 0–5，原 6 CPU / 16 GiB 不增加。
- 独立客户端容器使用 CPU 集合 6–7、2 CPU / 2 GiB；与服务端不重叠。
- 共享 PID/网络命名空间仅用于读取准确进程资源和保持原 127.0.0.1 连接路径；两者 CPU cgroup 独立。
- 客户端对 QCT 生产源码/构建/数据卷只读挂载，证据写入新命名卷；不挂载 Tenant-TTL 卷。
- 同一隔离条件先做 TP/PT 两对社区对照，再以多进程客户端按 ABC、ACB、BAC、BCA、CAB、CBA 六块完成社区/OFF/ON。
- B/OFF 与 C/ON 都固定 `46ca14950dc76004c5df355ce2c975a77c50041a`，使用同一组产物。
- 结束后停止客户端容器及四个测试节点，恢复服务端原 CPU 有效执行范围，保留新卷和所有构建、日志、数据。原空配置无法通过空参数清除，本次采用显式 `0-7`，不是配置字节级原样恢复。

这里的隔离是客户端与服务端 CPU 集合及配额隔离，并不是两台物理机器。仍共享 VM、宿主、内存系统、操作系统缓存和网络；其他现有容器不调整，仍可能使用这些 VM CPU。因此不能把本次称为物理 CPU/整台 VM 独占。

容器 `starrocks-query-corruption-perf-client`、独立卷 `sr-query-corruption-client-perf-arm64`；服务端原挂载/内存/CPU 配额不变。宿主控制器 `/private/tmp/qct-client-perf.YpMWTT/split_suite.py`，主日志同目录 `split-suite-20260922-r1.log`。服务端证据 `logs/QCT-007/split-client-20260922-r1/`，客户端新卷 `results/split-client-20260922-r1/`。约 08:15～09:16 UTC 完成 22 组 / 220,000 正式请求及 167,902 预热样本。

### 3.3 客户端限制是否已经排除

18 个 A/B/C 组，四个客户端进程合计约 0.63～0.67 核，占 2 核预算的一部分，客户端 cgroup 限流累计为 0；服务端约 4.85～4.98 核，服务端配额限流累计约 0.003 秒。旧单进程四线程的明显限制得到控制，不再用原约 100 QPS 的平台来判断服务端吞吐。

但“平均 CPU 有余量”不是所有瞬间都没有客户端等待的证明。结果网络传输、解码、调度仍包含在端到端时间中；两核客户端也不是无限算力。尚未用真实 JDBC 客户端、额外客户端 CPU 扩展或独立物理主机验证所有客户端影响，不能写成“彻底排除客户端的任何影响”。

本场景支持的结论是：**平均吞吐基本一致，未发现稳定的单向吞吐回退；ON 的 P99 点估计仍高约 2.02 ms / 4.62%，尾延迟等效性未证明。** 不设未经用户确认的百分比通过线，不将该结果推广到所有查询、协议或生产 SLO。

## 4. 判断方法

客户端模型变化若在正反顺序重复下都显著改变同一社区版本吞吐/尾延迟，说明原测试客户端是性能限制因素。客户端 CPU/查询下降与返回后消费耗时下降是辅助证据；没有客户端 CPU/GIL 采样时，不将差值全部定量归为某个解释器函数或 GIL。

隔离后的 A/B/C 只使用该阶段同条件配对，保留所有组和负面点估计。按独立运行块计算几何平均变化，少量块的 bootstrap 仅为探索性区间；区间包含 0 不证明零影响或性能等效。

如果客户端 CPU 留有余量且无配额限流，能够减轻先前单进程上限的混淆，但仍不能承诺任何驱动、SQL、并发、数据规模都不受客户端影响，也不能据固定并发 4 宣称服务端最大 QPS。
